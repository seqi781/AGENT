# 04 - 工具系统

> 时间：2026-06-10 · 对应代码：`agent/tools/`

## 设计哲学

工具是模型的"手"。工具设计的好坏直接影响分数（事前分析估计影响 2~5 分），核心原则：

1. **描述要"规定性"**：不只说工具是什么，还要说**什么时候用、什么时候不要用**（比如 run_command 的描述里明确写了"cd 不会保留到下一条命令"、"不要运行交互式程序"）。模型的困惑大多源自工具语义模糊。
2. **错误信息是给模型看的**：工具失败时返回的文本要能引导模型自我纠正（比如 edit_file 匹配不到时提示"请先 read_file 确认内容完全一致"）。
3. **输出在源头截断**：超长输出（如 `cat` 一个大文件）保留头尾、砍掉中间——关键信息通常在两端（开头是结果、结尾是报错）。不截断的话一条命令就能把上下文窗口撑爆。

## M1 的五个工具

| 工具 | 作用 | 关键设计点 |
|---|---|---|
| `run_command` | 执行 shell 命令（bash -c） | 独立进程、有超时（默认120s，可调）、stdout/stderr/退出码一起返回；退出码非 0 标记为错误 |
| `read_file` | 读文件，带行号 | 行号便于后续 edit 定位；支持 offset/limit 分页读大文件 |
| `write_file` | 整体写入文件 | 避免模型用 echo/heredoc 写文件时的转义灾难 |
| `edit_file` | 精确字符串替换 | str_replace 语义：old_string 必须**恰好出现一次**，出现 0 次或多次都报错并指导模型修正 |
| `task_done` | 宣告任务完成 | 显式结束信号；描述里强调"先验证再宣告" |

### 为什么有了 run_command 还要文件工具？

`cat`/`sed`/`echo` 理论上全能，但是：多行内容的 shell 转义极易出错；带行号读取 + str_replace 编辑是各家模型被大量训练过的"熟悉格式"，错误率显著更低。冒烟测试也验证了这点——模型自然地选择了 read_file → edit_file → write_file 的组合。

### 为什么 M1 不能跑交互式程序？

subprocess 是"一发一收"：命令运行完才能拿到全部输出，没法中途输入。要跟 vim、REPL、密码提示这类交互程序打交道，需要 tmux 后端（把命令"打字"进一个持久终端会话，随时读屏幕快照）——这是 M2 的内容，也是 terminal-bench 部分任务的硬需求。

## 代码结构

- `base.py` 的 `Tool` 基类负责：JSON 参数解析、参数错误转为给模型的提示、异常兜底、输出截断。子类只需声明 `name/description/parameters` 并实现 `run()`。
- `ToolResult.stop` 字段是结束信号通道：`task_done` 置 True，循环看到即退出。
- 新增工具 = 新建一个文件 + 注册进 `default_toolset()`，不碰其他代码。
