# 09 - 推理链重构：治"思考撞顶"

> 时间：2026-06-10 · 对应代码：`agent/core.py`（FIRST_TURN_PROTOCOL、NUDGE_REASONING_CAP、NUDGE_CAP_PIVOT）

M2 跑出 0.4 之后，失败轨迹里反复出现同一种死法：模型一轮里**什么都没说、什么工具都没调**，API 返回 `finish_reason="length"`。这不是模型偷懒，是它的私有推理（reasoning）撞上了服务端约 16k token 的单轮思考上限，被整段丢弃。我们把这叫"撞顶"。

## 根因：推理是一次性的，撞顶等于全损

DeepSeek 的 API 是无状态的：模型每轮的私有思考**不会带到下一轮**。这造成一个恶性循环：

```
任务复杂 → 模型想在脑内推演完整设计 → 超过 16k 被截断
→ 这轮零产出,思考全丢 → 下一轮从头重推同样的设计 → 再次撞顶 → ...
```

分析 17 个撞顶事件，触发点高度集中在两类时刻：**信息收集完毕后的"设计时刻"**（开始构思整体方案），和**在脑内起草整个大文件**。普通的"你没调工具，请继续"提醒对此完全无效——它只会让模型"再想一遍"，然后再撞一次。

## 修复一：首轮协议，把开局从开放题变成填空题

撞顶最高发的是第一轮：此时模型自由度最大，最容易直接开始推演全局。解法是把第一轮的格式钉死——任务后面附加一段协议，要求模型**不要深思**，只做两件事：用 `update_memory` 写下交付物清单和 3-6 步计划，同一轮里立刻发出第一批信息收集调用。深度思考推迟到拿到真实环境数据之后，一步一步来。

## 修复二：撞顶后的定向抢救，先缩步、再换路

撞顶后的提醒必须告诉模型三个事实：你刚才想的**全丢了**、重想**还会被截断**、所以**把步子缩小**。第一次撞顶时要求它挑一个最小的子问题，要么写个小脚本算出来，要么用十行以内的可见文字写出答案记到板上。

如果同一个地方**连续第二次**撞顶，说明缩步子也救不了——这条路本身对单轮思考太重。此时提醒升级为"换路"：放弃当前路线，换更笨但更轻的办法（暴力解、近似解、现成的库、先解决简化版）。这条对应行为分析里的一个铁律：高分 agent 的标志是失败后能改道，而不是死磕。

抢救配额按"每次事故"给而不是整个任务只给一次：连续撞顶最多救 3 次（`max_cap_rescues`），但只要模型恢复正常行动，配额就重置——长任务中段撞一两次很常见，每次抢救只花一轮约 75 秒，实证成功率约三分之二，值得给机会。

## 验证

用之前因撞顶全军覆没的 7 道题重跑：**0/7 → 4/7**。regex-log、polyglot-c-py 由首轮协议救活（根本没再撞顶）；feal-linear、schemelike 撞了顶但被定向抢救拉回来完成。剩下 3 道的死因转移到了别处（见 [10](10-memory-board.md)）——这正是我们想要的：架构病治好后，剩下的是模型能力边界。
